# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

The current prototype uses a plud-inspired 640px editorial shell for Zahirul Iman's portfolio. Use Saans as the primary type family and Saans Mono only for compact metadata, while preserving local project assets, the direct animated light/dark toggle, restrained surfaces, and Zahirul's positioning as a Product Designer & Digital Product Builder unless the user explicitly requests a redesign.

The portfolio typography uses a compact semantic scale: .6875rem micro metadata, .75rem captions, .8125rem labels, .875rem secondary text, 1rem body copy, 1.125rem lead text, 1.25rem subheadings, 1.5rem section headings, and fluid 1.625–2rem primary headings. Use roughly 400 for body copy, 520 for interface emphasis, and 620 for strong headings. Keep all displayed sizes mapped to these semantic tokens instead of adding one-off pixel values. Load the converted Saans variable and Saans Mono Regular WOFF2 files from `/public/assets/fonts` so deployed pages use same-origin font requests with no dependency on GitHub availability. Keep system sans and monospace fallbacks. Do not add additional Saans static cuts unless a demonstrated typography need justifies another request.

Keep the menu and light/dark controls together as one compact top-right control rail. The menu control must retain a visible Menu/Close label except on very narrow phones, use a real CSS morphing glyph rather than the unreliable stroked-SVG mask, and anchor the full-screen menu reveal to its position. Theme changes should use a restrained circular View Transition emitted from the theme control when supported, with an immediate reduced-motion fallback.

Use the supplied monochrome creative-tools illustration as the main hero visual, directly above the opening introduction.

Once the main hero illustration has fully left above the viewport, reveal a slim fixed fabric-style ribbon tab aligned to the left edge of the 640px content column. Use a downward arrow point rather than an inverted swallow-tail cut, keep the fabric surface free of inset border or stitch lines, and let its entrance settle with a short damped fabric-like motion. The ribbon contains the locally generated transparent head-only portrait derived from the main creative-tools illustration, stays beneath the menu layer, and retracts when the hero illustration returns. Clicking it plays the optimized local one-shot transparent `zahirul-camera-motion-fast.webp` in which the head lowers, the camera portrait rises and recoils, then the normal portrait returns; the normal and animated states must retain the same perceived head scale. Preload and decode the animated asset before enabling the ribbon, keep the static head visible until the animation’s first frame is ready, and start flash/reset timing from that actual media-ready event so the first mobile click never blanks, lags, or desynchronizes. Avoid filters on the animated image. Synchronize one full-viewport white camera flash to the recoil. Do not strobe or repeat automatically; reduced-motion users receive only the static camera portrait swap without the flash.

Motion should feel quiet, precise, layered, and editorial. Use one choreographed hero entrance, then viewport-triggered motion only for meaningful chapter arrivals: staggered copy layers, media reveals, true list staggering, the activity grid, the featured SesiFoto card, and the chat shell. Let these entrances replay smoothly after an element fully leaves and later re-enters the viewport. Keep continuous motion extremely subtle and limited to the hero illustration plus contextual loops such as typing and hover-triggered fire. Avoid generic whole-section fade-and-rise repetition, continuous parallax, bounce, elastic easing, or blocking interactions. Fully disable decorative motion for reduced-motion preferences.

The initial portfolio load uses a short, visually distinct full-viewport loading screen containing only a restrained centred percentage. Do not add a name, mark, loading label, progress bar, or other decoration. Use a quiet green-grey loading surface that is visibly different from the normal white or near-black page background, with an equally restrained contrasting percentage in both light and dark themes. Its initial `00%` state must be present directly in `index.html` with minimal inline critical styles so it paints from the first millisecond, before React and the main stylesheet load, then hands off seamlessly to the interactive loader. Apply the saved light or dark theme synchronously in the document head and keep the `html`, `body`, and `#root` boot backgrounds fixed to that theme so the HTML-to-React handoff never exposes a white frame. Progress must be tied to readiness of the critical Saans font and hero illustration, include only a brief minimum display for a seamless handoff, have a safety timeout so it cannot hang, and transition cleanly into the homepage. Reduced-motion visitors skip the loader choreography after the initial HTML paint. Keep the optimized transparent WebP as the displayed hero and menu illustration; retain the PNG only for social sharing metadata.

Animate only `.route-stage`, and do not retain its transform after the entrance finishes, so fixed navigation and full-screen chat remain anchored to the viewport.
